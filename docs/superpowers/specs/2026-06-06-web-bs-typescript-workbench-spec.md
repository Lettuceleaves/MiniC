# MiniC Web BS TypeScript Workbench SPEC

## Goal

Build a browser/server version of MiniC Visual Workbench that reuses the existing `minic.uiapi` boundary and reproduces the current JavaFX UI feature set in a TypeScript web client.

The result must run as a B/S architecture:

```text
Browser TypeScript Workbench
  -> REST + WebSocket network layer
      -> Java Web Adapter
          -> MiniCObservationApi / MiniCDebugApi / realtime analysis facade
              -> existing session / runtime / compiler
```

The browser UI must be a real usable Workbench on first load, not a landing page. It must support source editing, compiler observation, stage visualization, debugger controls, data-structure visualization, settings, keyboard/mouse viewport controls, and current regression coverage parity with the JavaFX implementation.

## User Intent

The user wants the current JavaFX Workbench experience reproduced for web usage under B/S deployment. The existing `minic.uiapi` layer is the required application boundary. Browser code must not know compiler, runtime, stepper, session, AST, IR, Scope, or DebugSession internals. The web layer must add network transport and TypeScript UI while preserving the clean layering already present in the project.

## Non-Goals

1. Do not replace or remove the JavaFX Workbench.
2. Do not rewrite compiler, runtime, session, or uiapi internals to fit the web UI.
3. Do not expose compiler/runtime/session objects directly through HTTP.
4. Do not introduce server-side rendering for the Workbench.
5. Do not add Electron or a desktop browser shell.
6. Do not add authentication, multi-tenant authorization, or persistent user accounts in this phase.
7. Do not guarantee safe execution of arbitrary untrusted C programs beyond the explicit local execution restrictions already required in this spec.
8. Do not make visual redesign the goal. The target is functional and interaction parity first, with web-native polish second.

## Selected Stack

### Frontend

- Language: TypeScript.
- Framework: React.
- Build tool: Vite.
- Routing: TanStack Router.
- Server state: TanStack Query.
- Client UI state: Zustand.
- UI primitives: Radix UI.
- Styling: Tailwind CSS plus a small layer of app-specific CSS variables.
- Code editor: Monaco Editor.
- Graph rendering: React Flow as the default graph layer.
- Large graph fallback: Cytoscape.js only when React Flow cannot meet performance acceptance for data-structure graphs.
- Unit/component tests: Vitest + React Testing Library.
- E2E and screenshot tests: Playwright.

### Backend Network Adapter

- Language: Java 21, because `minic.uiapi` is Java and must stay in-process with the compiler/runtime model.
- Package: `minic.web`.
- HTTP framework: Javalin.
- JSON mapper: Jackson.
- API contract: OpenAPI 3 document checked into the repo and used to generate TypeScript DTO/client types.
- Transport: REST for commands and queries; WebSocket for state/event push.

### Rationale

React + Vite gives the fastest path to a complex SPA Workbench in TypeScript without SSR overhead. TanStack Query matches the server-state nature of `Ui*Dto` snapshots. Zustand handles local layout and viewport state without duplicating server DTOs. Monaco is the most appropriate browser editor for source editing, diagnostics, gutter markers, and future language support. React Flow maps well to AST/scope/data-structure graph views. Javalin keeps the Java adapter small, testable, and close to `minic.uiapi`.

## Git And Phase Commit Discipline

Every implementation phase in this SPEC is a required commit boundary. A phase is not complete until its scoped files are committed after the phase acceptance checks pass.

### Phase 0: Specification And Planning Commit

Before implementation begins, commit the SPEC and execution plan updates as a documentation-only phase:

- Commit only `docs/superpowers/specs/2026-06-06-web-bs-typescript-workbench-spec.md` and the execution plan file under `docs/superpowers/plans/`.
- Do not stage existing dirty worktree changes outside those paths.
- Commit message: `docs(web): phase 00 bs workbench spec and execution plan`.
- Verification before commit: run the SPEC incomplete-marker scan and confirm all required sections are present.

### Pre-Phase Git Checklist

Before starting each implementation phase:

1. Run `git status --short`.
2. Record unrelated pre-existing changes and avoid touching them.
3. Read any target file that already has uncommitted changes before editing it.
4. If a target file contains user changes unrelated to the current phase, preserve them and stage only the intentional phase diff.
5. Do not use destructive Git commands such as `git reset --hard` or `git checkout --` during this work.

### Staging Rules

Stage only explicit paths for the current phase. Do not use `git add .`, `git add -A`, or wildcard staging from the repository root.

Acceptable examples:

```powershell
git add -- build.gradle src/main/java/minic/web/MiniCWebApplication.java src/test/java/minic/web/MiniCWebApiRegressionTest.java
git add -- docs/api/minic-web-openapi.yaml web/package.json web/src/api/generated/schema.d.ts
```

Unacceptable examples:

```powershell
git add .
git add -A
git commit -am "..."
```

### Commit Message Rules

Use one commit per completed phase, with this format:

```text
<type>(web): phase <NN> <short phase name>
```

Allowed types:

- `docs` for SPEC, plan, API documentation, and user-facing documentation.
- `build` for Gradle, npm, generated client plumbing, and packaging setup.
- `feat` for production behavior.
- `test` only when a phase intentionally contains tests without production behavior.
- `fix` only for corrections discovered while executing a later phase.

Examples:

```text
build(web): phase 01 backend launcher
feat(web): phase 04 compile rest routes
feat(web): phase 10 workbench ui parity
docs(web): phase 12 release readiness
```

### Verification Before Commit

For each phase:

1. Run every acceptance command listed for that phase.
2. Run the architecture import checks relevant to files changed in that phase.
3. Run `git diff --check -- <phase paths>` before staging.
4. Commit only after checks pass.
5. If checks fail, do not commit partial code. Fix the phase or record the blocker in the execution log.

Generated files must be committed in the same phase as the generator configuration and command that produced them.

### Phase Completion Record

After each phase commit, record these items in the execution log or final progress report:

- Phase number and name.
- Commit hash.
- Files changed by the phase.
- Acceptance commands run.
- Result of each command.
- Any deviation from the SPEC and its justification.

Do not amend, squash, reorder, or rewrite prior phase commits during implementation. Corrections found later must be committed in the phase where they are discovered, or in an explicit `fix(web): phase <NN> ...` correction commit if the current phase cannot proceed without it.

## Architecture Rules

### Dependency Direction

Allowed:

```text
minic.web -> minic.uiapi
minic.web -> minic.source
minic.web -> Java/Javalin/Jackson
web/src -> generated OpenAPI types
web/src -> browser APIs, React, Monaco, React Flow
```

Forbidden:

```text
minic.compiler -> minic.web
minic.runtime -> minic.web
minic.session -> minic.web
minic.uiapi -> minic.web
minic.web -> minic.ui
web/src -> JavaFX concepts except as renamed Workbench feature concepts
web/src -> compiler/runtime/session internal object shapes
```

The web backend may call `MiniCObservationApi` and `MiniCDebugApi`. It may not call `CompileObservationSession`, `StageStepper`, `DebugSession`, compiler AST classes, IR classes, or runtime debug internals directly.

### Session Model

Every browser session must map to server-owned state:

```text
CompileWebSession
  id
  createdAt
  lastAccessedAt
  MiniCObservationApi
  sourceName
  sourceText
  playbackState
  lock

DebugWebSession
  id
  createdAt
  lastAccessedAt
  MiniCDebugApi
  sourceName
  sourceText
  breakpoints
  lock
```

Rules:

1. Session IDs must be random, non-sequential, and URL-safe.
2. Each session must serialize its own commands through a per-session lock or executor.
3. Different sessions may run concurrently.
4. Idle sessions must expire.
5. Closing a session must release references to source text, API objects, pending timers, and WebSocket subscribers.
6. Server shutdown must close all sessions.

### Network Semantics

REST is command/query transport.

WebSocket is notification transport. REST remains the source of truth for command completion. A WebSocket event may tell the browser what changed, but the browser may refetch the relevant REST resources through TanStack Query.

All server responses must be structured JSON. Exceptions must not leak Java stack traces to browser clients.

## WebSocket Contract

Endpoint:

```text
/ws
```

Client messages:

```text
subscribe.compile-session
unsubscribe.compile-session
subscribe.debug-session
unsubscribe.debug-session
ping
```

Server messages:

```text
session.created
session.closed
session.expired
compile.state.changed
compile.stage.changed
compile.visual.changed
compile.diagnostics.changed
compile.execution-output.changed
debug.state.changed
debug.breakpoint.changed
debug.view.changed
debug.event
settings.changed
error
pong
```

Each event must include:

```text
type
sessionId or debugSessionId when applicable
version
occurredAt
payload
```

The browser must tolerate missed WebSocket events by refetching snapshot endpoints after reconnect.

## Frontend Feature Parity

### App Shell

The web app must reproduce the Workbench structure:

- Left activity bar: Code, Debug, Settings, reserved activity sections currently present in JavaFX.
- Sidebar: stage list and source/session controls.
- Editor region: source editor or visual pane depending on mode.
- Inspector/right panel for compiler controls and status.
- Bottom panel: diagnostics, hover/selection explanation, output summaries.
- Document tabs with new/open/save-compatible browser behavior.
- Status bar with current mode, stage, playback state, and connection state.

Browser file operations must use web-safe behavior:

- Open local file via browser file picker.
- Save/download current source as `.mc`.
- The web app must not assume unrestricted filesystem write access.

### Source Editor

Monaco must support:

- MiniC source editing.
- Diagnostics markers from realtime analysis.
- Lexer token based syntax highlighting where available.
- Breakpoint gutter markers.
- Current debug execution line/range.
- Font zoom and vertical scrolling controls.
- Source load into compile and debug sessions.

### Compiler Observation

The UI must support:

- Start session.
- Next.
- Next stage.
- Run to execution.
- Play.
- 2x play.
- Pause.
- Tick behavior through server command and WebSocket notification.

- Lexer token view and source overlay.
- Parser AST graph.
- Semantic AST + scope view.
- IR view.

Graph views must support:

- Zoom in/out.
- Pan.
- Center active node or active range.
- Node click/hover explanation.

### Debugger

- Start debug.
- Breakpoint add/remove/sync from editor.
- Run to breakpoint.
- Run to end.
- Fast forward.
- Step over.
- Step into.
- Step out.

### Settings

### Keyboard, Mouse, And Viewport Controls

- Pinned target.

## Code Style Constraints

### Java

1. Use Java 21 language features already accepted in this project.
2. Keep new web classes small and responsibility-focused.
3. Use package `minic.web` only for network adapter code.
4. Use `Objects.requireNonNull` in constructors and records where applicable.
5. Use immutable response DTOs or records.
6. Use `List.copyOf`, `Map.copyOf`, or unmodifiable views for exposed collections.
7. Do not add JavaFX imports to `minic.web`.
8. Do not add web imports to compiler/runtime/session/uiapi.
9. Convert exceptions to structured web errors at the route boundary.
10. Do not print user-facing errors only to console.
11. Tests must use explicit assertions, not only smoke calls.
12. Avoid reflection. If reflection is needed for a DTO mapper, it must stay in existing uiapi mapper patterns and be covered by tests.

### TypeScript

1. Enable `strict`.
2. Enable `noUncheckedIndexedAccess`.
3. Enable `exactOptionalPropertyTypes`.
4. Avoid `any`. Use generated types, `unknown`, discriminated unions, or explicit domain types.
5. Do not use non-null assertions unless a nearby guard proves the condition and a comment explains the invariant.
6. Components must be function components with typed props.
7. Keep server state in TanStack Query, not Zustand.
8. Keep local UI state in component state or Zustand, not duplicated server DTO copies.
9. Put generated API types under `web/src/api/generated`.
10. Do not hand-edit generated API files.
11. Use stable query keys from `queryKeys.ts`.
12. Use typed command functions instead of ad hoc `fetch` calls in components.
13. Components should render empty, loading, error, and populated states.
14. Avoid CSS that depends on text length for layout stability.
15. Use accessible labels for icon-only or compact controls.

### CSS And UI

1. Use CSS variables for theme tokens.
2. Do not use one-off inline styles for recurring UI patterns.
3. Do not place cards inside cards.
4. Keep workbench layout dense and operational, not marketing-like.
5. Use stable dimensions for toolbars, icon buttons, gutters, graph controls, and tabs.
6. Text must not overlap or overflow controls at tested viewports.
7. Use responsive panel collapse only where desktop layout cannot fit.
8. Preserve the current Workbench's tool-first feel.

## Programming Habit Constraints

### Reuse First

1. Reuse `MiniCObservationApi` and `MiniCDebugApi`.
2. Reuse existing `Ui*Dto` shapes as the network response model.
3. Reuse existing settings/theme files where possible.
4. Reuse existing sample programs for tests and E2E flows.
5. Reuse existing visual semantics: active token, active AST node, active source range, scope direction, IR/ASM active line.
6. Add new abstractions only when at least two features need the same behavior or the boundary protects layering.

### Forbidden Risky Code

Java forbidden:

- `sun.misc.Unsafe` or `jdk.internal.misc.Unsafe`.
- JNI/native bridges.
- `System.exit` in web server code.
- `Runtime.exec` or `ProcessBuilder` in web adapter code for arbitrary user input.
- String-built shell commands.
- Reflection with `setAccessible(true)`.
- Global mutable singleton session state outside `MiniCWebSessionRegistry`.
- Unbounded thread creation.
- Unbounded queues.
- Wildcard CORS in production mode.
- Returning Java stack traces to browser clients.

TypeScript forbidden:

- `eval`.
- `new Function`.
- `dangerouslySetInnerHTML`.
- Raw `innerHTML`.
- Unvalidated `postMessage` handling.
- `as any`.
- `// @ts-ignore` and `// @ts-expect-error` unless the line is paired with an issue reference and a test proving runtime safety.
- Mutating generated DTO objects in-place.
- Storing secret or server-only values in local storage.
- Infinite retry loops.
- Silent catch blocks.

Shared forbidden:

- Swallowing errors without user-visible or test-visible consequences.
- Adding framework dependencies without documenting why existing stack cannot solve the problem.
- Directly copying JavaFX implementation details that are tied to JavaFX threading or controls.
- Reimplementing compiler/runtime logic in TypeScript.
- Mixing transport DTOs with mutable view models.

### Error Handling Requirements

Every network error must map to:

```text
status
code
message
details
requestId
```

Required codes:

```text
bad_request
session_not_found
session_expired
session_not_started
command_not_supported
compile_diagnostics
debug_diagnostics
execution_blocked
internal_error
```

Browser UI must show meaningful errors in the status bar or panel. It must not fail silently.

### Concurrency Requirements

1. Same session commands are serialized.
2. Repeated clicks on the same command while in flight are disabled or coalesced.
3. WebSocket events must be versioned.
4. Browser refetch must ignore stale responses when a newer version is already applied.
5. Play/pause race conditions must be covered by tests.

### Security And Local Execution Requirements

1. Web server defaults to localhost binding.
2. Production external binding requires explicit configuration.
3. CORS defaults to same-origin only.
4. Request body size limit must be set for source text.
5. Execution stage must have timeout and output size limits.
6. Toolchain/execution errors must return diagnostics or structured errors.
7. The web adapter must not expose file read/write endpoints beyond browser-safe source upload/download behavior.
