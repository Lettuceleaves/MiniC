## header
词法分析可以先理解成“给 C 源码分词”：它把一长串字符切成一个个 token，就像把一句话拆成词和标点。当前 token 是 ${kind}，它在源码里写成 `${text}`，位置从 ${startLine}:${startColumn} 到 ${endLine}:${endColumn}，offset 范围是 ${startOffset}..${endOffset}。Lexer 先负责认出这个片段属于哪一类，Parser 后面才不用一个字符一个字符地猜，而是直接根据 token 类别去组成声明、表达式和语句。位置信息也很重要，因为后续生成 AST、做类型检查或报语法错误时，都需要把问题准确指回原来的代码位置。

## footer
用途: token 是 Parser 的输入，也是 Lexer 交给语法分析阶段的“词语清单”。比如 `int x = 1;` 会被拆成类型关键字、标识符、运算符、字面量和分号，Parser 再按照语法规则把它们拼成一个变量声明节点。读懂当前 token 的类别、文本和位置，就能看出 Parser 为什么在这里组成某个 AST 节点。后续语义分析、错误提示和代码生成也会沿着这些 token 信息，追踪每一段程序来自源码的哪里。

## type_keyword
当前源码片段是 `${source}`，其中 `${text}` 被识别成类型关键字，也就是 C 代码里用来说明“接下来这个名字是什么类型”的词。比如 `int add(int a, int b) { return a + b; }` 里的函数返回类型和形参类型，`int x = 1;` 里的变量类型，以及 `struct Point { int x; int y; };` 里的结构体和字段类型，都要先被 Lexer 识别出来。Parser 看到这类 token 后，会把它们放进函数声明、变量声明或结构体声明的 AST 节点里。后续语义分析再根据这些类型信息检查赋值、返回值、函数调用和成员访问是否匹配。

## control_keyword
当前源码片段是 `${source}`，`${text}` 在这里被当作控制流关键字处理；在 C 代码里，它通常长得像 `if`、`else`、`while` 或 `return` 这样的词。比如 `if (1 < 2)` 告诉程序要根据条件决定走哪条分支，`return a + b;` 则表示函数要把一个结果交回调用者。Lexer 需要把这些词认成关键字，而不是普通名字，否则 Parser 就不知道后面应该按分支语句、循环语句还是返回语句来读。Parser 会据此构造对应的语句节点，后续阶段再检查位置是否合法，并把它们变成条件判断、跳转或函数返回。

## EXTERN
当前源码片段是 `${source}`，`${text}` 在这里告诉编译器“这个函数或变量在别的地方实现，这里只是先说明它存在”。例如调用 `printf("value=%d\n", 42)` 前，真实的 `printf` 实现通常来自运行库，源码里可能只需要有一个外部声明。Lexer 要单独识别 `extern`，这样 Parser 才能把它和后面的函数或变量声明连成一个带外部属性的声明节点。语义分析会记录这个符号的名字和类型，代码生成或链接阶段再知道这里需要引用外部目标文件或运行库里的实现。

## IDENTIFIER
当前这个名字写作 `${text}`，源码片段 `${source}` 正是 Lexer 看到的那一小段 C 代码。标识符就是程序员自己起的名字，在源码里看起来像 `add`、`a`、`b`、`x`、`printf`、`Point` 或 `values`。在 `int add(int a, int b)` 中，`add` 是函数名，`a` 和 `b` 是形参名；在 `values[0] = 2;` 中，`values` 是被访问的数组名。Lexer 识别标识符时只负责把这一串字符当作“名字”交出去，还不会判断它到底是变量、函数还是类型名；Parser 会把名字放进声明或表达式的 AST 节点，后续语义分析再查符号表。

## literal
当前源码片段是 `${source}`，`${text}` 是源码里直接写出来的值，不需要像变量名那样再去符号表里查。比如 `int x = 1;` 里的 `1`，`if (1 < 2)` 里的 `1` 和 `2`，以及 `printf("value=%d\n", 42)` 里的 `42`，都是程序文本中直接给出的常量值。Lexer 要把这些连续字符认成一个完整的 token，否则 Parser 很难知道 `42` 是一个数而不是两个分开的字符。Parser 通常会把它们变成常量表达式节点，后续阶段再决定把值放成立即数、常量数据，或者参与类型检查和常量折叠。

## STRING_LITERAL
当前源码片段是 `${source}`，`${text}` 是用双引号包起来的一整段字符串字面量，比如 `printf("value=%d\n", 42)` 中的 `"value=%d\n"`。它里面可能包含普通字符、格式占位符和转义序列，所以 Lexer 必须把从开引号到闭引号的整段内容识别成一个 token。这样 Parser 在分析函数调用时，才能把它当作一个完整实参，而不是一堆零散字符。后续阶段通常会把字符串内容放到常量数据区，并在生成 `printf` 这类调用时传入对应的字符串地址。

## operator
当前源码片段是 `${source}`，`${text}` 这个 token 表示源码里“要对值做什么操作”。比如 `a + b` 里的 `+`，`int x = 1;` 里的 `=`，以及 `if (1 < 2)` 里的 `<`，都需要 Lexer 从变量名、数字和分隔符中分出来。Parser 需要靠运算符判断表达式的结构和优先级，例如 `return a + b;` 会被组织成加法表达式再放进返回语句里。后续语义分析会检查运算符两边的类型是否允许这样用，代码生成阶段才会把它们落成具体的计算、比较或赋值指令。

## delimiter
当前源码片段是 `${source}`，`${text}` 这个分隔符很像 C 源码里的标点。比如 `int add(int a, int b) { return a + b; }` 中，圆括号圈出参数列表，花括号圈出函数体，逗号分开两个形参，分号结束 `return` 语句。Lexer 需要单独识别这些标点，因为 Parser 靠它们判断一组内容从哪里开始、在哪里结束，以及一个语句是否已经完整。后续阶段也会根据这些边界建立作用域、参数列表、结构体字段列表和数组下标访问，例如 `values[0] = 2;` 中的方括号就说明 `0` 是下标。

## EOF
当前 token 文本显示为 `${text}`，源码片段是 `${source}`；EOF 是 Lexer 在源码末尾补上的结束标记，它不对应某个真实写出来的字符，更像文章最后的结束提示。Parser 需要看到 EOF，才能确认 token 流已经读完，并判断整个程序是不是刚好在合法位置结束。比如如果源码写了 `struct Point { int x; int y; };`，Parser 读到 EOF 时就能确认结构体声明已经完整。反过来，如果读到 EOF 时还缺少右括号、右花括号、分号或表达式，报错就会围绕“输入已经结束但语法还没完成”来定位。

## default
当前源码片段是 `${source}`，token 文本是 `${text}`，类别是 `${kind}`；这一类表示 Lexer 已经把源码字符流切成了一个最小语法单元，但当前模板没有把它归到前面那些更具体的解释里。它在源码里仍然会像普通 token 一样出现，可能是某个符号、关键字或暂时没有专门说明的类别。Parser 依然会根据这个 token 的实际类别、文本和位置继续尝试组成合法语法结构。后续阶段如果发现它放错了位置，或者当前 MiniC 语法还不支持这种写法，就会借助这些信息生成更准确的提示。
